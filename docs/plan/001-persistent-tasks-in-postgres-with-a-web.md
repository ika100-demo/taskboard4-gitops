## taskboard4-gitops — Postgres for taskboard4-api, two API instances in dev, API address for taskboard4-web

**Shape:** `gitops-app` · **Criteria:** AC-001.1, AC-001.2, AC-001.6 · **Depends on:** []

The system has no resources yet. This entry declares the platform's `postgres` resource, wires it into
`taskboard4-api` (`DATABASE_URL` and `PG*` variables), raises the dev instance of `taskboard4-api` to two
replicas (AC-001.2 requires two instances in dev; run as `cplat component set taskboard4-api --instance dev
--replicas 2`, since the plan's operation list has no replicas operation) and gives `taskboard4-web` the
in-cluster API address `TASKBOARD4_API_URL=http://taskboard4-api` (the ClusterIP Service `taskboard4-api`,
port 80, in the same namespace). Both components are already exposed in dev, so no `expose` operation is
needed, and the API's exposure stays as it is (non-goal).

It owns the deployment half of AC-001.1 (a database that outlives API pods), AC-001.2 (two instances) and
AC-001.6 (the web app can reach the API). Database backups are out of scope (non-goal).

It goes first: the persistent API needs `DATABASE_URL` on its first dev rollout. Between this PR and the
API's merge, dev runs two in-memory instances, so lists can differ per instance for that short window; this
is expected and ends when the API lands.

## taskboard4-api — Keep tasks in Postgres, answer 503 and report not ready while the database is down

**Shape:** `service-python` · **Criteria:** AC-001.1, AC-001.2, AC-001.3, AC-001.4, AC-001.5 · **Depends on:** [taskboard4-gitops]

Replaces the process-local `TaskStore` with a Postgres-backed store behind the same interface; the HTTP
routes and models stay unchanged (AC-001.3). Decisions:

- **Schema:** one table `tasks` with `seq bigserial primary key` (creation order), `id uuid unique not null`
  (generated by the API, returned as a string, as today), `title varchar(200) not null`, `due_date date null`,
  `created_at timestamptz not null default now()`. `GET /tasks` orders by `seq`: one sequence across all
  instances gives a single global oldest-first order (AC-001.1, AC-001.2).
- **Schema creation:** a versioned migration applied by the service when it first reaches the database,
  guarded so two instances starting together cannot both apply it (a Postgres advisory lock, or idempotent
  `CREATE ... IF NOT EXISTS`). The service must start and serve `/health` while the database is down; it
  creates the schema once the database is reachable, without a restart (AC-001.5).
- **Connections:** a connection pool with a connect timeout and statement timeout (see Timeouts); a broken
  connection is discarded and re-established on the next request, so recovery needs no restart (AC-001.5).
- **Validation before storage:** a body that fails validation answers `422` even when the database is
  down; only valid requests touch the database (AC-001.3, AC-001.4).
- **Readiness:** `/ready` runs a cheap database check (`SELECT 1`) and answers `503` when it fails;
  `/health` (liveness) never touches the database, so Kubernetes takes an instance out of the Service
  instead of restarting it during an outage (AC-001.5).

Tests: acceptance tests run against a real Postgres (testcontainers or the devbox Postgres), including a
"restart" test that builds a fresh app/store over the same database (AC-001.1), a two-app-instances test
over one database (AC-001.2), the full spec 001 contract suite re-run against Postgres (AC-001.3), and
database-down tests (stopped container or unreachable DSN) checking `503` within 10 s, no row written, `/ready`
not ready, and recovery after the database returns (AC-001.4, AC-001.5). Component AC-001.10 of spec 001 is
withdrawn there (see arguments).

## taskboard4-web — Task list and create form on the root page, talking to the Task API

**Shape:** `web-nextjs` · **Criteria:** AC-001.6, AC-001.7, AC-001.8, AC-001.9, AC-001.10, AC-001.11, AC-001.12 · **Depends on:** []

Replaces the starter page at `/` with the task list and the create form. Decisions:

- **All API calls run on the Next.js server**, using `TASKBOARD4_API_URL` (never exposed to the browser,
  no `NEXT_PUBLIC_` variable, no CORS). The root page is a dynamic server component (`force-dynamic`, no
  caching) that calls `GET /tasks` per request.
- **Create** goes through a Server Action that calls `POST /tasks` and returns either the created task or
  a save error; the client component appends the returned task to the list without a reload, then clears the
  form (AC-001.8, AC-001.9). On a save error it keeps the title and due date and shows the save message
  (AC-001.12).
- **Due date** is a native `<input type="date">`; its value is already `YYYY-MM-DD` and is sent as is, an
  empty value is sent as `null`. Shown as the stored string, or "No due date" when `null` (AC-001.6). No
  minimum date (past dates accepted, AC-001.9).
- **Title** is checked on the client and again in the Server Action: after trimming, empty means "Title is
  required" next to the field and no API call (AC-001.10). The input has `maxLength={200}`.
- **Load failure** (any error, timeout or non-`200` from `GET /tasks`, or a body that is not an array of
  tasks): the page still renders, with the load message in place of the list; the create form stays
  (AC-001.11).
- `/api/ready` does not depend on the API: the page must load while the API is down (AC-001.11).

Tests: unit/component tests with the API client mocked at its HTTP boundary for every message and state;
Playwright e2e against a stubbed Task API (a small mock server on `TASKBOARD4_API_URL`) for AC-001.6 to
AC-001.12, and a `@smoke` test against the deployed dev app for the create-and-list path.

## Contract

The Task API (`taskboard4-api`) serves the web app's Next.js server. In dev the base URL is
`TASKBOARD4_API_URL=http://taskboard4-api`. The request/response contract of component spec
001-create-and-list-tasks is unchanged; this plan adds the `503` outcome and the readiness behaviour.

**Task object** (JSON): `{"id": string, "title": string, "due_date": string | null}`. `id` is a non-empty
opaque string (a UUID today; callers must not parse it). `title` is trimmed, 1 to 200 characters.
`due_date` is `"YYYY-MM-DD"` or `null`. No other fields; callers ignore unknown fields if any appear.

### `POST /tasks`

- Request: `Content-Type: application/json`, body `{"title": string, "due_date": string | null}`;
  `due_date` may be omitted (same as `null`). The web app sends `due_date: null` for an empty date field.
- `201 Created`: body is the created Task object, title trimmed.
- `422 Unprocessable Entity`: validation failed, no task stored. Body is FastAPI's standard
  `{"detail": [{"loc": ["body", "<field>"], "msg": string, "type": string}, ...]}`; `loc[-1]` names the
  offending field (`title` or `due_date`). An invalid JSON body also answers `422`. Validation runs before
  the database is touched, so `422` is returned even while the database is down.
- `503 Service Unavailable`: the database is unreachable or did not answer in time; no task stored. Body
  `{"detail": "database unavailable"}`.

### `GET /tasks`

- `200 OK`: a bare JSON array of Task objects, oldest first (creation order across all instances); `[]`
  when there are none. No pagination.
- `503 Service Unavailable`: the database is unreachable or did not answer in time. Body
  `{"detail": "database unavailable"}`.

### Probes (platform, not the web app)

- `GET /health`: `200 {"status": "ok"}` whenever the process runs; never touches the database.
- `GET /ready`: `200 {"status": "ready"}` when `SELECT 1` succeeds; `503 {"status": "not ready"}` when it
  fails or times out.

### Errors

- Error bodies are JSON with a `detail` key: a list of validation entries for `422`, a string for `503`
  and for unexpected `500`s.
- The web app maps outcomes as follows. `GET /tasks`: only `200` with a JSON array counts as success; any
  other status (`503`, `500`, `404`, ...), a malformed body, a connection error or a timeout shows "Tasks
  could not be loaded. Please try again later." `POST /tasks`: only `201` with a Task object counts as
  success; any other status (including `422`, which cannot happen after the web app's own title check,
  and `503`), a malformed body, a connection error or a timeout shows "The task could not be saved.
  Please try again." with the form kept and nothing added to the list.
- A caller treats any status this contract does not list exactly like `503`: a failure, with no
  assumption that a task was or was not stored. The web app does not retry automatically.
- The web app logs the failure on its server (status or error kind, no task content beyond the id);
  error details from the API are never shown to the person.

### Timeouts

- **Web server -> API:** `GET /tasks` and `POST /tasks` each with a 5 s total timeout (connect plus
  response); on timeout the call counts as failed (see Errors). No retries.
- **API -> Postgres:** connect timeout 3 s, statement timeout 5 s, waiting for a pooled connection at most
  2 s; any of them expiring answers `503`. Together the API answers within 10 s in the worst case
  (AC-001.4); in practice an unreachable database answers in about 3 s.
- **`/ready`:** the database check uses a 0.5 s timeout so the probe answers within the kubelet's default
  1 s probe timeout; on expiry it reports `503 not ready`.
- **Database down:** the API keeps running (liveness stays green), answers `503` on task calls, and is
  taken out of the Service by readiness. With both instances not ready, the Service has no endpoints and
  the web app's calls fail fast with a connection error, which it treats as above. When the database
  returns, the next request opens a fresh connection; no restart is needed (AC-001.5).
- **API down or slow:** the web page still renders within the 5 s budget with the load message
  (AC-001.11); a create shows the save message (AC-001.12).

## gitops-app PR

No version pins in this plan: the spec covers dev only, and dev tracks `main` (`gitops_pin` is empty);
staging and prod follow the usual pin policy later, after the database-backup spec.

Order: the taskboard4-gitops PR lands first (postgres resource, `uses: postgres` on taskboard4-api, two
dev replicas of taskboard4-api, `TASKBOARD4_API_URL` on taskboard4-web); taskboard4-api and taskboard4-web
merge afterwards (web may merge any time). After Argo reconciles dev, verify:

- the postgres resource is healthy and the `taskboard4-api` pods carry `DATABASE_URL` and `PG*`;
- `taskboard4-api` runs two ready pods in dev;
- `taskboard4-web` pods carry `TASKBOARD4_API_URL=http://taskboard4-api`;
- after the API merges: create a task through `POST /tasks`, delete both API pods, and `GET /tasks` still
  returns it (AC-001.1); ten `GET /tasks` calls all contain it (AC-001.2);
- after the web merges: `http://taskboard4-web.taskboard4-dev.localhost/` lists the tasks and creates one.
